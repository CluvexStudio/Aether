# ایتر

ایتر یک کلاینت پروکسی در فضای کاربر برای Cloudflare WARP است. از دل یک شبکه‌ی
فیلترشده یک تونل می‌سازد و یک پروکسی SOCKS5 محلی روی `127.0.0.1:1819` باز
می‌کند. مرورگر، ترمینال یا پروکسی سیستم را به همان نشانی وصل کنید تا ترافیک از
تونل بیرون برود.

نه به دسترسی روت نیاز دارد و نه درایور شبکه نصب می‌کند. همه چیز درون خود پروسه
اتفاق می‌افتد: تونل، یک پشته‌ی TCP/IP در فضای کاربر، و پروکسی.

## اجرا

`aether` را بدون آرگومان اجرا کنید تا چند سؤال بپرسد، یا فلگ بدهید تا چیزی
نپرسد. هر فلگ یک متغیر محیطی معادل هم دارد، پس همان تنظیمات در کانتینر یا
سرویس هم کار می‌کند. `aether --help` همه را فهرست می‌کند.

```sh
aether
aether --masque --scan balanced
aether --wg --noize aggressive --bind 127.0.0.1:1080
```

برای اطمینان از کار کردن:

```sh
curl -x socks5h://127.0.0.1:1819 https://www.cloudflare.com/cdn-cgi/trace
```

پاسخ باید یک colo کلادفلر و `warp=on` نشان بدهد.

برای کلاینت‌هایی که SOCKS نمی‌فهمند، یک پروکسی HTTP CONNECT هم اضافه کنید:

```sh
aether --http-proxy 127.0.0.1:1820
```

هر دو لیسنر روی همان تونل کار می‌کنند. آن‌ها را فقط وقتی به `0.0.0.0` ببندید که
عمداً می‌خواهید تونل را با شبکه‌تان به اشتراک بگذارید؛ هیچ احراز هویتی روی
تماس‌گیرنده‌ها انجام نمی‌شود.

## پروتکل‌های انتقال

| انتقال | فلگ | حامل |
| --- | --- | --- |
| MASQUE | `--masque` (پیش‌فرض) | QUIC/HTTP-3 روی UDP 443 یا HTTP/2 روی TCP 443 |
| WireGuard | `--wg` | وایرگارد روی UDP 2408 و پورت‌های جایگزین مستند |
| WireGuard روی MASQUE (gool) | `--gool` | یک تونل وایرگارد داخل یک تونل MASQUE |
| WARP در WARP (gool کلاسیک) | `--gool-classic` | یک تونل وایرگارد داخل تونل دیگر |

MASQUE پیش‌فرض است چون شکل ترافیک HTTPS معمولی را دارد و کلادفلر هم آن را
پروتکل اصلی می‌داند. وقتی QUIC روی UDP محدود شده ولی UDP ساده رد می‌شود،
WireGuard را بردارید. `--gool` یک هاپ دوم اضافه می‌کند: شبکه‌ی شما فقط تونل
MASQUE را می‌بیند و هاپ وایرگارد داخل آن از درون WARP وصل می‌شود، پس کلادفلر
خروجی دیگری به آن می‌دهد، نه خروجی‌ای که نشانی خودتان می‌گرفت.
`--gool-classic` به‌جای آن وایرگارد را داخل وایرگارد می‌گذارد. هر دو تأخیر
اضافه می‌کنند، پس آخرین گزینه باشند.

MASQUE دو حامل دارد. HTTP/3 روی QUIC پیش‌فرض است. اگر UDP 443 کلاً بسته باشد،
`--h2` همان تونل را روی TCP 443 می‌برد که از شبکه‌هایی که QUIC را دور می‌ریزند
عبور می‌کند.

```sh
aether --masque --h2
```

## پیدا کردن نقطه‌ی اتصال

کلادفلر روی نشانی‌های لبه‌ی متعددی جواب می‌دهد و یک شبکه‌ی فیلترشده معمولاً
بخشی از آن‌ها را می‌بندد، پس ایتر یک نشانی ثابت ندارد. رنج‌های مستند را جاروب
می‌کند، کاندیداها را می‌سنجد و آن را که ترافیک واقعی را حمل می‌کند نگه می‌دارد.
هندشیک تنها کافی نیست: هر کاندیدا باید یک بررسی داده‌ی سرتاسری را پاس کند تا
پروکسی به کار بیفتد.

| حالت | رفتار |
| --- | --- |
| `turbo` | روی اولین کاندیدایی که جواب بدهد می‌ایستد |
| `balanced` | پیش‌فرض، چندتا جمع می‌کند و سریع‌ترین را برمی‌دارد |
| `thorough` | کل رنج‌ها را جاروب می‌کند، وقتی همه چیز بسته به نظر می‌رسد |
| `stealth` | پروب کم و همزمانی پایین، برای شبکه‌هایی که اسکن را می‌بینند |
| `ironclad` | برای هر کاندیدا یک تونل کامل و یک درخواست HTTP واقعی |

اگر نشانی خوبی را از قبل می‌دانید، اسکن را رد کنید:

```sh
aether --peer 162.159.196.1:443
```

آخرین نقطه‌ی سالم ذخیره می‌شود و `--quick-reconnect` بدون جاروب جدید از همان
استفاده می‌کند. نقطه‌ای که همین حالا شکست خورده، مدتی در فهرست انتظار می‌ماند تا
تلاش بعدی دوباره روی آن نیفتد.

### دادن دستی نشانی هاپ‌های gool

`--gool` فقط یک هاپ را اسکن می‌کند، یعنی گیت‌وی MASQUE را، که مثل خود MASQUE
با `--peer` داده می‌شود. هاپ وایرگارد داخل تونل اسکن نمی‌شود: همان نقطه‌ای است
که ثبت‌نام هویت gool نام می‌برد، و بعد چند نقطه‌ی شناخته‌شده، روی پورت 2408،
مگر اینکه `--gool-peer` نقطه‌ی دیگری را نام ببرد:

```sh
aether --gool --peer 162.159.196.1:443 --gool-peer 162.159.192.1:2408
```

gool کلاسیک، یعنی WARP در WARP، به دو نقطه‌ی وایرگارد نیاز دارد و `--peer` یکی
را نام می‌برد، پس هر هاپ تنظیم خودش را دارد. هر دو را بدهید و هیچ اسکنی اجرا
نمی‌شود؛ یکی را بدهید و اسکن دنبال آن یکی می‌گردد:

```sh
aether --gool --wiw-outer 162.159.192.1:2408 --wiw-inner 188.114.96.1:2408
aether --gool --wiw-peers 162.159.192.1:2408,188.114.96.1:2408
aether --gool --wiw-outer 162.159.192.1:2408   # هاپ داخلی اسکن می‌شود
aether --gool --wiw-inner 188.114.96.1:1701    # هاپ بیرونی اسکن می‌شود
```

نوشتن پورت الزامی است و هیچ پورتی برایتان فرض نمی‌شود: اینکه کدام پورت جواب
می‌دهد دقیقاً همان چیزی است که از یک شبکه به شبکه‌ی دیگر فرق می‌کند، پس پورت
فرض‌شده فقط شما را به نشانی‌ای می‌فرستد که کسی پیشنهادش نداده. دو هاپ هم باید
روی دو نشانی متفاوت باشند — تونل دوم اگر از همان لبه‌ای بیرون برود که از آن
آمده چیزی اضافه نمی‌کند — و اسکنی که برای یک هاپ اجرا می‌شود نشانی آن یکی را
از جاروب کنار می‌گذارد.

نام بردن یک هاپ خودش gool کلاسیک را انتخاب می‌کند، پس `--gool` یا
`--gool-classic` در کنارش اختیاری است. با `--gool-classic`، `--wg-peer` هم هاپ
بیرونی را نام می‌برد. نشانی‌ای که خودتان داده‌اید در اتصال‌های دوباره حفظ می‌شود
و جای خود را به نتیجه‌ی اسکن نمی‌دهد، پس هاپی که جواب ندهد دوباره امتحان می‌شود
نه اینکه عوض شود. `--wiw-scan` هر دو را اسکن می‌کند و نشانی باقی‌مانده در محیط
را نادیده می‌گیرد.

هیچ‌کدام از این‌ها موقع شروع پرسیده نمی‌شود. `--gool-classic` به‌تنهایی هر دو
هاپ را اسکن می‌کند و بالای سؤال حالت اسکن یک خط می‌نویسد که راه دیگر را نشان
می‌دهد.

## مبهم‌سازی

بعضی شبکه‌ها بسته‌های اول یک هندشیک را انگشت‌نگاری می‌کنند. ایتر می‌تواند آن‌ها
را پد و بازشکل کند تا تبادل ابتدایی با الگوی شناخته‌شده جور نشود.

| پروفایل | چه وقت |
| --- | --- |
| `off` | شبکه بازرسی نمی‌کند |
| `light` | مزاحمت خفیف، کمترین سرباری |
| `balanced` | پیش‌فرض، نقطه‌ی شروع خوب |
| `aggressive` | هندشیک دارد انگشت‌نگاری می‌شود |

```sh
aether --noize aggressive
```

یک مورد به ClientHello در TLS مربوط است: `--fragment` آن را روی حامل HTTP/2 در MASQUE
تکه می‌کند و بازرس‌هایی را که SNI را از یک بسته می‌خوانند خنثی می‌کند، و ClientHello
فراخوانی‌های WARP API را هم، با هر پروتکلی. `--fragment-size` و `--fragment-delay`
هر دو را تنظیم می‌کنند. بدون `--fragment` هر دو یک‌تکه می‌روند.

## TLS

چهار نوع هندشیک TLS تونل و راه‌اندازی آن را می‌برند: MASQUE روی HTTP/3 و روی HTTP/2،
درخواست‌ها به API وارپ، و جست‌وجوی DNS-over-HTTPS برای کانفیگ ECH. هر چهار،
ClientHello مرورگر Chrome را همان‌طور که BoringSSL می‌نویسد می‌فرستند: TLS 1.3 و 1.2،
سوئیت‌های رمز Chrome، مقدارهای GREASE (RFC 8701)، افزونه‌ها با ترتیبی تازه در هر
هندشیک، و درخواست signed certificate timestamps و OCSP. مثل Chrome اول `h2` و بعد
`http/1.1` را پیشنهاد می‌دهند، جز روی QUIC که `h3` را پیشنهاد می‌دهد و فقط TLS 1.3 را
حمل می‌کند؛ حامل HTTP/2 با HTTP/2 کار می‌کند که کلادفلر انتخابش می‌کند. گواهی‌ها
بررسی نمی‌شوند، جز گواهی گیت‌وی MASQUE با `--team` یا `--tls-verify` که باید با یکی از
pinهای ایتر مطابق باشد. ورود به Zero Trust، فهرست پل‌ها و رله‌های Tor و جست‌وجوی محل
خروج TLS خودشان را دارند. شانزده گزینه اثرانگشت هر چهار را تغییر می‌دهند:

- `--tls-ciphers` سوئیت‌های رمز TLS 1.2 را تعیین می‌کند که بعد از سوئیت‌های TLS 1.3
  می‌آیند. نام‌ها با `:` از هم جدا می‌شوند، همان‌طور که BoringSSL یک رشته‌ی رمز را
  می‌خواند. HTTP/3 هیچ‌کدام را نمی‌آورد. بدون آن، سوئیت‌ها همان سوئیت‌های Chrome
  هستند، از قاعده‌ی خود Chrome یعنی `ALL:!aPSK:!ECDSA+SHA1:!3DES`، با ترتیب Chrome:
  روی سخت‌افزاری که دستورهای AES دارد اول AES-GCM و جاهای دیگر اول ChaCha20.
- `--tls13-ciphers` سوئیت‌های رمز TLS 1.3 را به ترتیب تعیین می‌کند: نام‌های
  استانداردشان که با `:` از هم جدا می‌شوند، از میان `TLS_AES_128_GCM_SHA256`،
  `TLS_AES_256_GCM_SHA384` و `TLS_CHACHA20_POLY1305_SHA256`، هر کدام یک بار. بدون آن،
  با ترتیب Chrome می‌آیند: روی سخت‌افزاری که دستورهای AES دارد اول AES-GCM و جاهای
  دیگر اول ChaCha20. BoringSSL همیشه آن‌ها را پیش از سوئیت‌های TLS 1.2 می‌آورد.
- `--tls-groups` گروه‌ها را به ترتیب تعیین می‌کند (پیش‌فرض `P-256:X25519:P-384`).
- `--tls-key-shares` گروه‌هایی را به ترتیب تعیین می‌کند که ClientHello برایشان سهم
  کلید (key share) می‌فرستد: هر کدام یکی از گروه‌ها، به ترتیب خود گروه‌ها، و یک بار؛
  مثلاً `X25519MLKEM768:X25519:P-256` با
  `--tls-groups X25519MLKEM768:X25519:P-256:P-384:P-521`، همان‌طور که Firefox
  می‌فرستد. بدون آن، انتخاب BoringSSL است، مثل Chrome: گروه اول، و اولین گروه از نوع
  دیگر، پساکوانتومی یا نه.
- `--disable-grease` مقدارهای GREASE را کنار می‌گذارد، که هر چهار در غیر این صورت در
  سوئیت‌های رمز، افزونه‌ها، گروه‌ها، سهم‌های کلید و نسخه‌ها می‌گذارند.
- `--enable-grease-sigalgs` یک مقدار GREASE را هم در ابتدای الگوریتم‌های امضا
  می‌گذارد، مثل Chrome؛ BoringSSL به‌طور پیش‌فرض آن را نمی‌گذارد. با
  `--disable-grease` یا بدون آن کار می‌کند.
- `--tls-sigalgs` الگوریتم‌های امضایی را که ClientHello فهرست می‌کند به ترتیب تعیین
  می‌کند، و در نتیجه الگوریتم‌هایی را که سرور می‌تواند هندشیک را با آن‌ها امضا کند:
  نام‌های BoringSSL که با `:` از هم جدا می‌شوند، مثل `ecdsa_secp256r1_sha256`،
  `rsa_pss_rsae_sha256`، `rsa_pkcs1_sha1`، `ed25519` یا `mldsa65`، هر کدام یک بار.
  بدون آن، فهرست BoringSSL است: هشت الگوریتم Chrome و بعد `rsa_pkcs1_sha1`.
- `--tls-cert-compression` فشرده‌سازی گواهی (RFC 8879) را به ترتیب پیشنهاد می‌دهد،
  از میان `zlib`، `brotli` و `zstd` که با `:` از هم جدا می‌شوند: `brotli` همان‌طور که
  Chrome پیشنهاد می‌دهد و `zlib:brotli:zstd` همان‌طور که Firefox. گواهی‌ای که سرور با
  یکی از آن‌ها فشرده بفرستد باز می‌شود و باید دقیقاً به طولی برسد که سرور گفته است.
  بدون آن، هیچ‌کدام پیشنهاد نمی‌شود.
- `--tls-alps new` یا `--tls-alps old` تنظیمات برنامه (ALPS) را برای HTTP/2 و HTTP/3
  پیشنهاد می‌دهد، بی هیچ تنظیمی از سمت کلاینت، مثل Chrome: `new` با کدی که Chrome
  اکنون می‌فرستد (0x44cd) و `old` با کدی که پیش‌تر می‌فرستاد (0x4469)، مثل Chrome 120.
  HTTP/1.1 هیچ ALPSی نمی‌گیرد. بدون آن، ALPS پیشنهاد نمی‌شود.
- `--tls-trust-anchors` گواهی‌ای از لنگرهای اعتمادی (trust anchors) می‌خواهد که نام
  می‌برد (draft-ietf-tls-trust-anchor-ids): شناسه‌هایشان، OIDهای نسبی به شکل اعداد
  نقطه‌دار مثل `11129.9.1`، که با `:` از هم جدا می‌شوند، به ترتیب، همان‌طور که Chrome
  لنگرهای خودش را می‌خواهد. هیچ بررسی گواهی را تغییر نمی‌دهد.
- `--tls-server-padding <n>` از سرور `n` بایت padding در هندشیکش می‌خواهد، از 0 تا
  65535، همان‌طور که Chrome ‏6000 بایت می‌خواهد (افزونه‌ی server_padding در
  BoringSSL). سروری که آن را نشناسد نادیده‌اش می‌گیرد.
- `--enable-ech-grease` وقتی کانفیگ ECHی برای پیشنهاد نیست، یک
  encrypted_client_hello از نوع GREASE می‌فرستد که شبیه ECH است و چیزی را پنهان
  نمی‌کند، مثل Chrome و Firefox. با `--ech`، خود کانفیگ به جای آن می‌رود.
- `--disable-ocsp-stapling` و `--disable-sct` درخواست OCSP (status_request) و
  درخواست signed certificate timestamps را کنار می‌گذارند، که هر چهار در غیر این صورت
  مثل Chrome می‌فرستند.
- `--disable-session-ticket` افزونه‌ی session_ticket را کنار می‌گذارد، که هر چهار در
  غیر این صورت مثل Chrome می‌فرستند.
- `--disable-extension-permutation` افزونه‌ها را با ترتیب ثابت BoringSSL نگه می‌دارد،
  در هر هندشیک یکسان، همان‌طور که افزونه‌های Firefox، Python و Go هستند؛ در غیر این
  صورت هر بار با ترتیبی تازه می‌آیند، مثل Chrome.

مقداری که این گزینه‌ها نپذیرند هسته را در شروع، با نام همان گزینه، متوقف می‌کند: رمز،
گروه یا الگوریتم امضایی که BoringSSL نشناسد، سهم‌های کلیدی که از گروه‌ها پیروی نکنند،
نامی که دو بار آمده باشد، کد ALPSی جز `new` و `old`، شناسه‌ی لنگر اعتمادی که عدد
نقطه‌دار نباشد، یا paddingی بیش از 65535.

بعضی از چیزهایی که کلاینت‌های دیگر می‌فرستند از BoringSSL برنمی‌آید:
delegated_credentials، record_size_limit، signature_algorithms_cert،
encrypt_then_mac، post_handshake_auth و بیش از یک قالب نقطه (point format). همیشه
با TLS 1.3 افزونه‌ی psk_key_exchange_modes را می‌فرستد، برای هر گروه سهم کلید جداگانه
می‌سازد و افزونه‌ها را با ترتیب خودش می‌چیند.

هندشیک‌های MASQUE، روی هر دو حامل، `www.cloudflare.com` را به‌عنوان نام سرور در
ClientHello می‌گذارند؛ `--masque-sni <name>` نام دیگری را به‌جای آن می‌گذارد، مثلاً
`consumer-masque.cloudflareclient.com` که کلاینت WARP می‌فرستد. فقط نام TLS عوض می‌شود: میزبان HTTP، یعنی `:authority` درخواست CONNECT، همان
`cloudflareaccess.com` می‌ماند. این نام در همه‌ی هندشیک‌های MASQUE می‌رود: اسکن و
بررسی گیت‌وی‌ها، خود تونل، و هر دو هاپ MASQUE-in-MASQUE (`--mim`). با `--ech` این نام
درون ClientHello رمزشده می‌رود و نامی که آشکار فرستاده می‌شود نام عمومی (public name)
کانفیگ است. مقداری که دامنه نباشد، از جمله نشانی IP، هسته را در شروع متوقف می‌کند.

`--ech auto` یک کانفیگ Encrypted Client Hello می‌گیرد و اگر شبکه اجازه بدهد نام سرور
را کاملاً پنهان می‌کند، در هندشیک‌های MASQUE روی هر دو حامل و در درخواست‌ها به API
وارپ. این کانفیگ را از رکورد HTTPS دامنه‌ی `cloudflare-ech.com` و با پرسیدن از
`udp://1.1.1.1` می‌گیرد؛ `--ech-dns` سرور DNS دیگری را تعیین می‌کند (`udp://ip[:port]`
یا `tcp://ip[:port]` که بی‌پورت روی پورت 53 است، یا آدرس `https://` یک سرور
DNS-over-HTTPS که بی‌پورت روی پورت 443 است) و `--ech-domain` دامنه‌ی دیگری را. بعد از
آدرس DNS-over-HTTPS، `@address=` اتصال را به نشانی IP یا دامنه‌ی دیگری می‌برد، روی
پورت همان آدرس، و `@sni=` نام دیگری را در ClientHello می‌گذارد، و میزبان آدرس همان
میزبان HTTP می‌ماند: `https://doq.dns4all.eu/dns-query@address=2.2.2.2@sni=google.com`
به 2.2.2.2 وصل می‌شود، در ClientHello نام google.com را می‌فرستد و روی HTTP از
doq.dns4all.eu می‌پرسد. این جست‌وجو بدون ECH انجام می‌شود، چون کانفیگی که می‌گیرد همان
است که ECH لازم دارد. `--ech <base64>` به‌جای این کار خود کانفیگ را می‌گیرد، به همان
شکلی که مقدار `ech` در چنین رکوردی نوشته می‌شود. یک کانفیگ برای هر دو کافی است: نشستی
که بعد از درخواست‌ها به API وارپ شروع شود همان کانفیگ آن‌ها را پیشنهاد می‌دهد. اگر
کانفیگی برای ارائه نباشد، چه جست‌وجوی آن شکست خورده باشد و چه کانفیگ از نوعی نباشد که
کتابخانه‌ی TLS بتواند به کار ببرد، هیچ نامی آشکار فرستاده نمی‌شود: از API وارپ پرسیده
نمی‌شود، نشست MASQUE شروع نمی‌شود و هسته دلیلش را می‌گوید.

## Zero Trust

با `--team <name>` ایتر به‌عنوان یک دستگاه مدیریت‌شده در حساب Zero Trust سازمان
شما ثبت می‌شود، به‌جای اینکه یک دستگاه مصرفی ناشناس بسازد. روی MASQUE و
WireGuard هر دو کار می‌کند و یک هویت تیمی بین‌شان مشترک است، پس عوض کردن انتقال
یک ظرفیت دستگاه دیگر مصرف نمی‌کند.

سه راه ورود:

| روش | فلگ | مناسب |
| --- | --- | --- |
| کد ایمیلی | `--access-email <addr>` | کاربری که پشت کیبورد است |
| توکن سرویس | `--access-id`, `--access-secret` | سرور و CI |
| توکن آماده | `--access-token <jwt>` | توکنی که از قبل دارید |

```sh
aether --team acme --access-email me@example.com
```

کلادفلر یک کد یک‌بارمصرف ایمیل می‌کند و ایتر آن را می‌پرسد. کد را می‌توان در
ترمینال نوشت یا از ورودی استاندارد داد؛ کلاینت‌های دسکتاپ و اندروید از همین راه
جواب می‌دهند. سه تلاش دارید. توکن حاصل تا پایان عمر پروسه نگه داشته می‌شود، پس
اتصال دوباره سؤال را تکرار نمی‌کند.

روی MASQUE، با `--team` گواهی گیت‌وی با pinهای ایتر سنجیده می‌شود، همان‌طور که با
`--tls-verify`، تا یک واسط میانی نتواند با گواهی خودش جای گیت‌وی را بگیرد و ترافیک
داخل تونل را ببیند. `AETHER_TLS_VERIFY=0` این بررسی را خاموش می‌کند.

`--gateway` ترافیک HTTP و HTTPS را از پروکسی Gateway سازمان می‌برد تا فیلترینگ و
لاگ آن اعمال شود. پیش‌فرض خاموش است چون یک هاپ داخل تونل اضافه می‌کند و
مرورتان را ثبت می‌کند. اگر آن پروکسی از جواب دادن بیفتد، ایتر به خروج مستقیم از
تونل برمی‌گردد و همه‌ی اتصال‌ها را نمی‌شکند.

## قواعد مسیریابی

دو فهرست تعیین می‌کنند یک مقصد چه اجازه‌ای دارد. `--route-block` اتصال را کاملاً
رد می‌کند. `--route-direct` آن را از رابط واقعی شما بیرون می‌فرستد نه از تونل، که
همان چیزی است که اپ‌های بانکی، سرویس‌های شبکه‌ی محلی و سایت‌های داخلی که نشانی
خارجی را قبول نمی‌کنند لازم دارند. اول block بررسی می‌شود، بعد direct، در غیر
این صورت تونل.

```sh
aether --route-block ads.example.com,port:25 --route-direct private,bank.ir
```

| ورودی | چه چیزی را می‌گیرد |
| --- | --- |
| `example.com` | خود نام و همه‌ی زیردامنه‌ها |
| `full:example.com` | فقط همان نام دقیق |
| `keyword:doubleclick` | هر نامی که شامل آن باشد |
| `regexp:^ad[0-9]+` | یک عبارت باقاعده |
| `10.0.0.0/8` | یک شبکه، یا یک نشانی تنها |
| `port:25`, `port:3000-3010` | یک پورت یا یک بازه |
| `private` | فضای شبکه‌ی محلی، لوپ‌بک و CGNAT |

فهرست‌های بلند را در فایل بگذارید:

```ini
[block]
ads.example.com
port:25

[direct]
private
bank.ir
```

```sh
aether --routes /etc/aether/routes.conf
```

قواعد روی TCP و UDP هر دو اعمال می‌شوند. قاعده‌ی جدا برای هر برنامه عمداً اینجا
نیست: در حالت tun، ترافیک تا وقتی به ایتر برسد هویت برنامه‌اش را از دست داده،
پس آن تفکیک کار کلاینت پلتفرم است.

### قواعد نام پشت tun

قواعد نام وقتی هم که به پروکسی به‌جای نام یک نشانی داده می‌شود کار می‌کنند، یعنی
همان کاری که tun انجام می‌دهد. ایتر نام را از server name در TLS یا هدر `Host` در
اولین بایت‌ها برمی‌دارد و تصمیم را با آن می‌گیرد؛ اگر نامی پیدا نشود، قواعد نشانی
و پورت مثل قبل اعمال می‌شوند.

نام فقط برای تصمیم استفاده می‌شود، پس اتصال همچنان به همان نشانی‌ای می‌رود که
کلاینت خواسته است.

| متغیر | پیش‌فرض | کار |
| --- | --- | --- |
| `AETHER_ROUTE_SNIFF` | روشن | با `0` خاموش می‌شود |
| `AETHER_ROUTE_SNIFF_MS` | `400` | چند میلی‌ثانیه منتظر آن بایت‌های اول بماند |

## پروکسی بالادست

`--upstream` هر چیزی که ایتر باز می‌کند را از یک پروکسی دیگر می‌فرستد، یعنی روشی
که با آن ایتر را پشت یک VPN یا پروکسی درحال‌اجرا زنجیر می‌کنید.

```sh
aether --upstream socks5://127.0.0.1:1080
aether --upstream socks5://alice:s3cret@127.0.0.1:1080
aether --upstream http://proxy.example:8080
```

اگر فقط `host:port` بنویسید، SOCKS5 فرض می‌شود. نشانی IPv6 را داخل کروشه بگذارید.
رمزی که `@` یا `:` دارد را درصدکدگذاری کنید، یعنی `p@ss` می‌شود `p%40ss`.

| پروکسی | چه چیزی را حمل می‌کند |
| --- | --- |
| SOCKS5 با UDP associate | همه‌ی پروتکل‌ها: MASQUE روی HTTP/3 و HTTP/2، وایرگارد، `gool` |
| HTTP CONNECT | فقط حامل HTTP/2، چون CONNECT نمی‌تواند UDP حمل کند |

با پروکسی HTTP، پرچم `--h2` را اضافه کنید تا کل تانل روی TCP بماند:

```sh
aether --masque --h2 --upstream http://proxy.example:8080
```

اسکن نقطه‌ی اتصال، تماس‌های ثبت‌نام و واکشی ECH هم از پروکسی رد می‌شوند. مقصدی که
با `--route-direct` انتخاب شده رد نمی‌شود، چون کار آن قاعده دور زدن تانل است.

همین تنظیم با `AETHER_UPSTREAM` هم در دسترس است.

## فایل‌های هویت

در اجرای اول، ایتر یک دستگاه ثبت می‌کند و اعتبارنامه‌ها را کنار مسیر کانفیگ
می‌نویسد، پیش‌فرض `aether.toml`. فایل را نگه دارید: حذفش یعنی ثبت یک دستگاه
جدید.

| فایل | محتوا |
| --- | --- |
| `aether.toml` | هویت وایرگارد |
| `aether-masque.toml` | هویت MASQUE و گواهی‌اش |
| `aether-team-<name>.toml` | یک هویت برای هر تیم Zero Trust |
| `aether-*-lastconn.toml` | آخرین نقطه‌ی سالم |

با `--config`، `--wg-config` و `--masque-config` می‌توانید مسیرشان را عوض کنید.
این فایل‌ها کلید خصوصی دارند و فقط برای مالک خواندنی نوشته می‌شوند.

### وقتی یک هویت دیگر پذیرفته نمی‌شود

کلادفلر می‌تواند دستگاهی را که هنوز در فایل شما هست دیگر نپذیرد. در آن حالت هندشیک
همچنان موفق می‌شود و ترافیکی رد نمی‌شود، پس ایتر هویت ذخیره‌شده را در شروع بررسی
می‌کند و گزارش می‌دهد:

```text
[-] cloudflare no longer accepts the saved identity for device <id>
[-] the tunnel will handshake but carry no traffic until this identity is replaced
```

بعد یک دستگاه تازه ثبت می‌کند و فایل را بازنویسی می‌کند. با `AETHER_REPROVISION=0`
فقط به شما خبر داده می‌شود بدون اینکه چیزی جایگزین شود.

تنها رد شدن از سمت API حساب به حساب می‌آید. آفلاین بودن یا خوردن به محدودیت نرخ
هویت را دور نمی‌ریزد.

### جایی که از API وارپ پرسیده می‌شود

ثبت یک دستگاه، ثبت کلید MASQUE آن و به‌روزرسانی یک پروفایل درخواست‌هایی به API وارپ
هستند که همان‌طور که در بخش TLS آمده فرستاده می‌شوند. سه گزینه می‌گویند این
درخواست‌ها چطور بروند، و هر کدام که داده نشود از گزینه‌ی پیش از خودش پیروی می‌کند:

- `--api-host` میزبان HTTP است، سرآیند `Host` یا `:authority` در HTTP/2، که پورتی
  ندارد. پیش‌فرض آن `api.devices.cloudflare.com` است: نامی که کلاینت Cloudflare One
  از نسخه‌ی 2026.6.0 به آن درخواست می‌دهد، روی نشانی‌های مخصوص خودش،
  162.159.137.105 و 162.159.138.105.
- `--api-sni` نام سرور در ClientHello است، که پیش‌فرضش نام `--api-host` است. با
  `--ech` فقط درون ClientHello رمزشده می‌رود.
- `--api-address` جایی است که اتصال به آن می‌رود: یک نشانی IP یا یک نام دامنه، روی
  پورت 443 مگر اینکه پورتی بعد از آن بیاید، که آن‌وقت نشانی IPv6 داخل کروشه می‌رود،
  مثل `162.159.137.105`، `188.114.97.6:2053` یا `[2606:4700:7::a29f:8969]:443`.
  پیش‌فرض آن نام `--api-sni` روی پورت 443 است.

کلادفلر به درخواستی که نام سرور و میزبانش یکی نباشند، حتی بین نام‌های خودش، پاسخ 403
می‌دهد، و برای همین نام سرور از میزبان پیروی می‌کند. `--api-sni` را فقط برای یک واسط
از آن خودتان که نام دیگری می‌پذیرد، متفاوت با `--api-host` بدهید.

اگر نه `--api-sni` داده شود و نه `--api-host`، تلاشی که
`api.devices.cloudflare.com` به آن پاسخ ندهد بعد از آن با `api.cloudflareclient.com`
می‌رود: نامی که کلاینت‌های وارپ پیش‌تر به آن درخواست می‌دادند، روی نشانی‌های مشترک
کلادفلر، که همان API را به همان درخواست‌ها می‌دهد. پاسخ ندادن یعنی هیچ پاسخی نیاید،
یا ردی از سروری جز خود API بیاید، مثل صفحه‌ی خطای لبه‌ی کلادفلر یا یک واسط میانی؛
پاسخ موفق، یا رد کردنِ خود API، درخواست را روی همان نام نگه می‌دارد، و اگر API سرش
شلوغ باشد همان‌جا دوباره پرسیده می‌شود. نشانی از نام پیروی می‌کند مگر اینکه
`--api-address` داده شده باشد، و نامی که API با آن پاسخ دهد در باقی اجرا اول می‌آید و
نام دیگر همچنان پشت سرش می‌ماند.

با `--api-address` به‌تنهایی هم درخواست‌ها اول با نام تازه و بعد با نام قدیمی می‌روند.
واسطی از آن خودتان که فقط `api.cloudflareclient.com` را می‌شناسد از همین راه کار
می‌کند؛ `--api-host api.cloudflareclient.com` همه‌ی درخواست‌ها را مثل پیش از 2.3.7 با
نام قدیمی می‌فرستد.

اگر هیچ‌کدام از این سه گزینه داده نشود، درخواستی که هیچ‌کدام از دو نام به آن پاسخ
ندهد یک راه دیگر هم دارد: نامی که اول می‌آید، روی یک لبه‌ی جداگانه‌ی کلادفلر، اول
104.24.4.6 و بعد 104.18.0.6، برای شبکه‌ای که نشانی‌های خود API را می‌بندد یا به جای
آن‌ها پاسخ می‌دهد ولی راه یک لبه را باز می‌گذارد. ClientHello این راه هم مثل بقیه فقط
با `--fragment` تکه‌تکه می‌رود. وقتی یک لبه پاسخ داد، درخواست‌های بعدی همان اجرا اول
به همان لبه می‌روند.

یک نام دامنه در `--api-address`، یا نام سروری که جای آن را می‌گیرد، اول جست‌وجو
می‌شود، با `--upstream` به دست پروکسی و گرنه با resolver سیستم. با `--mark` و بدون
`--upstream` فقط نشانی IP پذیرفته می‌شود، چون آن جست‌وجو بیرون از علامت می‌رفت و به
داخل تونل برمی‌گشت. یک نشانی IP برای `--api-address` نام را از جست‌وجوی DNS هم دور
نگه می‌دارد، که با `--ech` مهم است.

هر درخواست، و هر تلاش آن، روی یک اتصال TCP و یک هندشیک TLS جدا می‌رود که درخواست
دیگری را حمل نمی‌کند؛ هر درخواست ورود به Zero Trust هم همین‌طور.

```sh
aether --register all --api-address 162.159.137.105
aether --register all --api-host api.cloudflareclient.com
```

## استفاده از ایتر به‌عنوان کتابخانه

جدا از باینری `aether`، این کریت `libaether.a` و `libaether.so` را هم با یک
واسط C می‌سازد، تا یک برنامه‌ی میزبان بتواند هسته را لینک کند نه اینکه آن را
به‌عنوان پروسه اجرا کند. کلاینت iOS به همین نیاز دارد، و یک برنامه‌ی Go هم
می‌تواند از راه cgo از ایتر استفاده کند.

```sh
cd aether
cargo build --release                # باینری و هر دو کتابخانه
cargo build --release --bin aether   # فقط باینری
```

واسط C دستگیره‌محور و مبتنی بر poll است نه callback، پس صدا زدنش از هر رانتایمی
امن است. `aether_core_start` کل مسیر را اجرا می‌کند و یک دستگیره‌ی کار
برمی‌گرداند، `aether_job_poll` وضعیت را می‌دهد و `aether_job_cancel` متوقفش
می‌کند. برای مرحله‌های جداگانه هم توابع مستقل هست: هویت، ورود Zero Trust، اسکن
نقطه‌ی اتصال، سنجش، و تونل. هر پاسخ JSON است، هر رشته‌ی برگشتی با
`aether_string_free` آزاد می‌شود، و هیچ panic از مرز بیرون نمی‌زند. هدر آن در
کلاینت اوبلیوین در `ios/Shared/aether.h` است.

مسیر داده کانال‌محور است و هیچ کد دستگاه tun ندارد، پس برنامه‌ی میزبان بسته‌ها
را مستقیم می‌دهد و می‌گیرد.

## متغیرهای محیطی

هر فلگ یک متغیر معادل دارد. اگر هر دو ست شوند، فلگ برنده است.

| متغیر | چه چیزی را تعیین می‌کند |
| --- | --- |
| `AETHER_SOCKS` | نشانی لیسنر SOCKS5 |
| `AETHER_HTTP_PROXY` | نشانی لیسنر HTTP CONNECT |
| `AETHER_PROTOCOL` | `masque`، `wg`، `gool` |
| `AETHER_SCAN` | حالت اسکن |
| `AETHER_NOIZE` | پروفایل مبهم‌سازی |
| `AETHER_IP` | `4`، `6`، `dual` |

## اجرای پایدار در Termux با tmux

اگر Aether را روی **Termux** اجرا می‌کنید و می‌خواهید پروکسی آن را در اختیار دستگاه دیگری قرار دهید، پیشنهاد می‌شود Aether را داخل یک نشست `tmux` اجرا کنید.

`tmux` باعث می‌شود با خروج از Termux، بستن پنجره ترمینال یا قطع شدن اتصال SSH، نشست Aether باقی بماند و بتوانید بعداً دوباره به همان نشست متصل شوید.

### نصب tmux

در Termux:

```bash
pkg install tmux
```

### اجرای Aether داخل tmux

یک نشست با نام `aether` بسازید:

```bash
tmux new -s aether
```

سپس Aether را اجرا کنید:

```bash
aether
```

یا با تنظیمات دلخواه:

```bash
aether --masque --scan balanced
```

بعد از اجرای Aether، برای خارج شدن از نشست بدون بستن آن، کلیدهای زیر را بزنید:

```text
Ctrl + B
سپس D
```

اکنون نشست `tmux` جدا شده و Aether همچنان در آن نشست اجرا می‌شود.

### اتصال مجدد به Aether

هر زمان خواستید دوباره به نشست Aether متصل شوید:

```bash
tmux attach -t aether
```

برای مشاهده نشست‌های فعال:

```bash
tmux ls
```

### استفاده از Aether به‌عنوان پروکسی برای دستگاه دیگر

اگر می‌خواهید دستگاه دیگری در همان شبکه از پروکسی Aether استفاده کند، Aether را روی یک آدرس قابل دسترسی در شبکه اجرا کنید:

```bash
aether --bind 0.0.0.0:1819
```

سپس آدرس IP دستگاهی که Termux روی آن اجرا شده است را پیدا کنید:

```bash
ip addr
```

در دستگاه دیگر می‌توانید پروکسی SOCKS5 را به این شکل تنظیم کنید:

```text
socks5://IP-TERMUX:1819
```

برای مثال، اگر IP گوشی `192.168.1.20` باشد:

```text
socks5://192.168.1.20:1819
```

> **هشدار امنیتی:** باز کردن پروکسی روی `0.0.0.0` می‌تواند دسترسی به پروکسی را برای دستگاه‌های دیگر شبکه فراهم کند. فقط در شبکه‌ای که به آن اعتماد دارید از این حالت استفاده کنید.

### جلوگیری از توقف Aether در پس‌زمینه

`tmux` برای جلوگیری از بسته شدن نشست ترمینال بسیار مفید است، اما به‌تنهایی تضمین نمی‌کند که Android پردازش Termux را متوقف نکند.

برای پایداری بیشتر:

1. Battery Optimization برای Termux را غیرفعال کنید.
2. Termux را در حالت محدودشده توسط Battery Saver قرار ندهید.
3. در صورت نیاز از **Termux:Boot** برای اجرای خودکار پس از راه‌اندازی دستگاه استفاده کنید.
4. Aether را داخل `tmux` اجرا کنید تا با خروج از ترمینال، نشست آن بسته نشود.

### اجرای پیشنهادی برای اشتراک‌گذاری پروکسی

```bash
pkg install tmux
tmux new -s aether
aether --bind 0.0.0.0:1819
```

سپس برای جدا شدن از نشست:

```text
Ctrl + B
سپس D
```

برای اتصال مجدد:

```bash
tmux attach -t aether
```

`tmux` یک **terminal multiplexer** است که اجازه می‌دهد برنامه‌ها داخل یک نشست جداگانه اجرا شوند و پس از جدا شدن از ترمینال، نشست آن‌ها حفظ شود.
